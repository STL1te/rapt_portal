Локальный AI-ассистент обычно устроен не как «модель, внутри которой продолжается разговор», а как **обычное веб-приложение, которое при каждом сообщении заново передаёт модели нужную историю диалога**.

Сама LLM, запущенная через Ollama, llama.cpp, vLLM и т. п., в большинстве случаев **не помнит предыдущие HTTP-запросы**.

## Общая схема

```text
Браузер пользователя
        │
        │ POST /api/chat
        ▼
Backend твоего приложения
        │
        ├── загружает рецепт
        ├── загружает телеметрию
        ├── загружает историю диалога
        ├── формирует prompt/messages
        │
        ▼
Ollama / локальная LLM
        │
        ▼
Backend сохраняет ответ
        │
        ▼
Браузер показывает ответ
```

Допустим, пользователь открывает страницу рецепта:

```text
/recipes/123
```

На этой странице существует отдельная беседа:

```text
conversationId = 5d392...
recipeId = 123
```

Когда пользователь пишет:

> Почему брожение остановилось на 1.014?

Frontend отправляет на твой backend примерно это:

```json
{
  "conversationId": "5d392...",
  "message": "Почему брожение остановилось на 1.014?"
}
```

Frontend **не обязан сам отправлять всю историю**. Обычно он передаёт только ID беседы и новое сообщение, а историю собирает backend.

# Как выглядит запрос к модели

Большинство современных API используют формат сообщений с ролями:

```json
{
  "model": "gemma-4-12b-it",
  "messages": [
    {
      "role": "system",
      "content": "Ты AI-ассистент домашнего пивовара..."
    },
    {
      "role": "user",
      "content": "Вот данные рецепта и брожения..."
    },
    {
      "role": "assistant",
      "content": "Брожение находится на финальной стадии..."
    },
    {
      "role": "user",
      "content": "Почему тогда плотность уже сутки не меняется?"
    }
  ]
}
```

Модель получает весь этот массив и генерирует следующий ответ.

Она видит:

1. системные инструкции;
2. данные рецепта;
3. предыдущий вопрос;
4. предыдущий ответ;
5. новый вопрос.

Поэтому она может понять, что выражение «тогда плотность» относится к предыдущему обсуждению.

## Важный принцип

Модель не хранит такой объект внутри себя:

```text
conversationId → история разговора
```

Это делает твоё приложение.

После ответа модель забывает запрос. При следующем сообщении backend снова собирает:

```text
system prompt
+ контекст рецепта
+ предыдущие сообщения
+ новое сообщение
```

и снова отправляет это модели.

# Как это построить для ассистента пивовара

Я бы разделил входной контекст на четыре слоя.

## 1. Постоянный системный промпт

Он задаёт роль и правила поведения:

```text
Ты — AI-ассистент домашнего пивовара.

Твои задачи:
- анализировать рецепт;
- анализировать ход брожения;
- объяснять отклонения плотности и температуры;
- давать безопасные и практичные рекомендации;
- различать измеренные данные и предположения;
- учитывать погрешность плавающего гидрометра;
- не считать единичное изменение показаний доказательством тренда.

Всегда отвечай на русском языке.

При анализе брожения:
- сравнивай текущую плотность с OG, целевой FG и ожидаемой аттенюацией;
- анализируй изменение плотности во времени;
- учитывай температуру и свойства штамма дрожжей;
- не рекомендуй cold crash только на основании одного показания;
- явно отмечай недостаток данных.
```

Этот промпт обычно хранится в коде или базе как версия:

```text
brewing-assistant-v3
```

Версионирование полезно, чтобы понимать, почему старые и новые беседы ведут себя по-разному.

---

## 2. Контекст текущего объекта

Например, данные рецепта:

```text
РЕЦЕПТ

Название: Belgian Dubbel
Объём: 25 л
OG: 1.068
Расчётная FG: 1.013
Дрожжи: BVG-02 Dark Ale
Диапазон температуры: 18–24 °C
Хмель: ...
Засыпь: ...
Сахар: 500 г
```

И состояние брожения:

```text
ТЕКУЩЕЕ СОСТОЯНИЕ БРОЖЕНИЯ

Начало брожения: 18 июля 2026
Текущая плотность: 1.0141
Температура: 19.75 °C
Изменение за 24 часа: -0.0136 SG
Изменение за последние 6 часов: -0.0012 SG
Расчётная видимая аттенюация: 79.3%
```

Необязательно передавать модели тысячи точек телеметрии. Лучше заранее посчитать агрегаты:

```text
OG
текущая SG
минимальная SG
медиана за последние 3/6/12/24 часа
скорость изменения
разброс показаний
температурный тренд
длительность брожения
```

LLM лучше работает с компактным аналитическим контекстом, чем с 5000 сырыми строками JSON.

---

## 3. История диалога

Например:

```json
[
  {
    "role": "assistant",
    "content": "Брожение близко к завершению..."
  },
  {
    "role": "user",
    "content": "Есть смысл поднять температуру?"
  },
  {
    "role": "assistant",
    "content": "Да, можно плавно поднять до 21 °C..."
  }
]
```

---

## 4. Новое сообщение

```json
{
  "role": "user",
  "content": "А шпунт сейчас зажимать есть смысл?"
}
```

Модель понимает «сейчас» из переданного состояния брожения, а вопрос про шпунт — из истории разговора и контекста рецепта.

# Первый автоматический ответ на странице

Ты написал, что при открытии страницы рецепта должен выполняться запрос с дефолтным промптом.

Технически можно сделать так:

```http
POST /api/recipes/123/assistant/conversations
```

Backend:

1. создаёт новую беседу;
2. получает актуальные данные рецепта;
3. строит начальную инструкцию;
4. вызывает модель;
5. сохраняет ответ;
6. возвращает `conversationId` и сообщение.

Например, внутреннее первое сообщение может быть таким:

```text
Проанализируй текущий рецепт и состояние брожения.

Дай:
1. краткий итог;
2. основные наблюдения;
3. возможные проблемы;
4. рекомендации на ближайшие 24 часа.

Не повторяй все исходные данные подряд.
```

При этом его необязательно показывать пользователю как сообщение. В базе оно может существовать как внутренний trigger или скрытое сообщение.

Ответ:

```json
{
  "conversationId": "5d392...",
  "message": {
    "role": "assistant",
    "content": "Брожение находится на финальной стадии..."
  }
}
```

# Последующие вопросы

Пользователь пишет:

> Можно уже делать cold crash?

Frontend:

```http
POST /api/conversations/5d392/messages
Content-Type: application/json
```

```json
{
  "content": "Можно уже делать cold crash?"
}
```

Backend выполняет примерно такую логику:

```csharp
public async Task<string> SendMessage(
    Guid conversationId,
    string userMessage,
    CancellationToken cancellationToken)
{
    var conversation = await conversationRepository.GetAsync(
        conversationId,
        cancellationToken);

    var recipe = await recipeRepository.GetAsync(
        conversation.RecipeId,
        cancellationToken);

    var fermentation = await fermentationService.GetSummaryAsync(
        conversation.RecipeId,
        cancellationToken);

    await messageRepository.AddAsync(new ChatMessage
    {
        ConversationId = conversationId,
        Role = "user",
        Content = userMessage
    });

    var history = await messageRepository.GetRecentAsync(
        conversationId,
        limit: 20,
        cancellationToken);

    var messages = promptBuilder.Build(
        recipe,
        fermentation,
        history);

    var answer = await llmClient.ChatAsync(
        messages,
        cancellationToken);

    await messageRepository.AddAsync(new ChatMessage
    {
        ConversationId = conversationId,
        Role = "assistant",
        Content = answer
    });

    return answer;
}
```

Это базовая механика практически любого AI-чата.

# Как хранить диалоги

Минимальная схема PostgreSQL может выглядеть так.

## `ai_conversations`

```sql
create table ai_conversations
(
    id uuid primary key,
    recipe_id uuid not null,
    user_id uuid not null,
    title text,
    prompt_version text not null,
    created_at timestamptz not null,
    updated_at timestamptz not null
);
```

## `ai_messages`

```sql
create table ai_messages
(
    id uuid primary key,
    conversation_id uuid not null
        references ai_conversations(id),
    role varchar(20) not null,
    content text not null,
    created_at timestamptz not null,
    token_count integer
);
```

Роли обычно:

```text
system
user
assistant
tool
```

Но `system` необязательно сохранять как обычное сообщение. Его можно каждый раз строить заново из актуальной версии промпта.

# Почему нельзя бесконечно передавать всю историю

У модели есть ограничение контекстного окна, например:

```text
8 192 токена
32 768 токенов
128 000 токенов
```

В это окно входят:

```text
system prompt
+ рецепт
+ телеметрия
+ вся история
+ новый вопрос
+ будущий ответ
```

Допустим:

```text
system prompt       1 000 токенов
данные рецепта      1 500
телеметрия          2 000
история            10 000
новое сообщение       100
```

Итого уже 14 600 токенов.

При небольшом контексте ранние сообщения начнут обрезаться или модель не сможет сгенерировать достаточно длинный ответ.

Поэтому используют управление контекстом.

---

# Практичная стратегия контекста

Для твоего приложения я бы использовал:

```text
System prompt
+ актуальный контекст рецепта
+ краткое резюме старой части беседы
+ последние 10–20 сообщений
+ новый запрос
```

Например:

```text
КРАТКОЕ РЕЗЮМЕ БЕСЕДЫ

Пользователь анализирует брожение Belgian Dubbel.
Ранее решили постепенно поднять температуру с 18.5 до 21 °C.
Пользователь не планирует проводить вторичное брожение.
Предпочитает после завершения брожения переливать пиво прямо в кег.
Ассистент рекомендовал дождаться стабильной плотности минимум 24–48 часов.
```

После этого передаются последние сообщения буквально.

Это даёт модели и долгосрочный смысл разговора, и точную недавнюю формулировку.

## Когда делать summary

Например:

```text
если история > 12 000 токенов:
    взять старые сообщения
    сделать их краткое резюме
    сохранить summary
    старые сообщения больше не отправлять
```

Сами сообщения из базы удалять не нужно. Они остаются для отображения пользователю и возможной повторной обработки.

# Актуальные данные против старых данных

Это особенно важно в твоём случае.

Допустим, начальный ответ был сформирован при SG `1.020`, а через сутки SG стала `1.014`.

Если ты просто передашь старую историю:

```text
assistant: Текущая плотность составляет 1.020
```

модель может начать опираться на устаревшее значение.

Поэтому при каждом новом запросе нужно добавлять свежий блок:

```text
ВАЖНО:
Актуальные данные ниже имеют приоритет над значениями,
упомянутыми в предыдущих сообщениях.
```

А затем:

```text
Текущая плотность: 1.014
Последнее измерение: 23 июля 2026, 12:10
```

Так модель понимает, что `1.020` — историческая точка, а не текущее состояние.

# Не стоит смешивать данные с пользовательским сообщением

Плохой вариант:

```json
{
  "role": "user",
  "content": "Рецепт: {...огромный JSON...}. Телеметрия: {...}. Можно уже делать cold crash?"
}
```

Работать будет, но структура неочевидна.

Лучше формировать отдельный контекстный блок:

```json
[
  {
    "role": "system",
    "content": "Ты AI-ассистент пивовара..."
  },
  {
    "role": "system",
    "content": "Актуальный контекст рецепта и брожения:\n..."
  },
  {
    "role": "assistant",
    "content": "Предыдущий ответ..."
  },
  {
    "role": "user",
    "content": "Можно уже делать cold crash?"
  }
]
```

Некоторые модели неидеально обрабатывают несколько `system`-сообщений. Тогда всё объединяется в одно:

```text
[РОЛЬ И ПРАВИЛА]

...

[АКТУАЛЬНЫЕ ДАННЫЕ]

...

[ФОРМАТ ОТВЕТА]

...
```

# Ollama

Если ты используешь OpenAI-совместимый endpoint Ollama:

```http
POST http://homeserv.local:11434/v1/chat/completions
```

```json
{
  "model": "gemma-4-12b-it",
  "messages": [
    {
      "role": "system",
      "content": "Ты AI-ассистент домашнего пивовара."
    },
    {
      "role": "system",
      "content": "Рецепт: Belgian Dubbel. OG: 1.068..."
    },
    {
      "role": "user",
      "content": "Можно уже делать cold crash?"
    }
  ],
  "temperature": 0.3,
  "stream": true
}
```

При `stream: true` ответ приходит кусочками:

```text
data: {"choices":[{"delta":{"content":"Брожение"}}]}
data: {"choices":[{"delta":{"content":" уже"}}]}
data: {"choices":[{"delta":{"content":" близко"}}]}
```

Backend может проксировать эти кусочки браузеру через:

```text
Server-Sent Events
WebSocket
обычный chunked HTTP response
```

Для простого чата SSE обычно достаточно.

# Потоковая схема

```text
Пользователь отправил вопрос
          │
          ▼
Frontend добавляет временное сообщение пользователя
          │
          ▼
POST /api/conversations/{id}/messages
          │
          ▼
Backend начинает streaming от Ollama
          │
          ▼
"Брожение"
"Брожение близко"
"Брожение близко к завершению..."
          │
          ▼
После завершения backend сохраняет полный ответ
```

Пользователь видит, как ответ печатается постепенно, хотя модель на самом деле просто отдаёт токены по мере генерации.

# Нужно ли хранить состояние в Ollama

Нет. Не стоит рассчитывать, что Ollama будет управлять твоими пользовательскими беседами.

Разделение ответственности лучше такое:

```text
PostgreSQL:
- пользователи;
- рецепты;
- сессии брожения;
- беседы;
- сообщения;
- резюме бесед.

Твой backend:
- авторизация;
- сбор контекста;
- ограничение доступа;
- построение промпта;
- выбор модели;
- управление контекстом;
- вызов инструментов.

Ollama:
- только inference модели.
```

Некоторые API возвращают внутренний context/cache, который можно передать обратно. Но для полноценного продукта лучше хранить логическую историю у себя, а не привязываться к внутреннему формату конкретного inference-сервера.

# Инструменты для ассистента

Следующий уровень — не запихивать все данные в prompt, а позволить модели запрашивать их через tools.

Например:

```text
get_recipe(recipeId)
get_latest_fermentation_state(sessionId)
get_telemetry_summary(sessionId, period)
get_yeast_info(yeastId)
calculate_attenuation(og, fg)
calculate_abv(og, fg)
```

Пользователь спрашивает:

> Какая была скорость падения плотности за последние сутки?

Модель сначала возвращает вызов инструмента:

```json
{
  "name": "get_telemetry_summary",
  "arguments": {
    "sessionId": "abc",
    "period": "24h"
  }
}
```

Backend выполняет функцию и передаёт результат обратно модели:

```json
{
  "role": "tool",
  "content": {
    "startGravity": 1.0182,
    "endGravity": 1.0141,
    "delta": -0.0041,
    "medianRatePerDay": -0.0038
  }
}
```

После этого модель формирует человеческий ответ:

> За последние 24 часа медианная плотность снизилась примерно на 0.0038 SG. Брожение всё ещё продолжается, хотя уже замедляется.

Это надёжнее, чем заставлять LLM самой анализировать массив из тысяч точек.

# Что я рекомендую сделать в первой версии

Для MVP не нужны ни сложный RAG, ни агенты.

Архитектура:

```text
React / Blazor frontend
        │
ASP.NET Core API
        ├── PostgreSQL
        ├── RecipeContextBuilder
        ├── ConversationContextBuilder
        └── OllamaClient
                │
             Ollama
```

Каждый запрос:

```text
1. Получить conversationId.
2. Сохранить новое сообщение пользователя.
3. Получить рецепт.
4. Получить актуальную сводку телеметрии.
5. Получить summary старой беседы.
6. Получить последние 10–20 сообщений.
7. Собрать messages.
8. Отправить в Ollama.
9. Передавать ответ стримом клиенту.
10. Сохранить полный ответ.
```

Структура prompt:

```text
SYSTEM:
роль, ограничения, методика анализа

CURRENT CONTEXT:
актуальный рецепт и состояние брожения

CONVERSATION SUMMARY:
резюме старого разговора

RECENT MESSAGES:
последние сообщения

USER:
новый вопрос
```

Именно так диалог будет выглядеть естественным: пользователь сможет писать «а температуру?», «а если ещё сутки подождать?», «ты же говорил поднять до 21», и модель будет понимать, к чему относятся эти фразы.
